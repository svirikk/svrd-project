# Strung. — String Art Studio

Односторінковий сайт для генерації прев'ю string-art портрета з фото клієнта
й оформлення замовлення напряму в Telegram (без бази даних) + застосунок
покрокового складання для клієнта (`/assembly/`).

**Це ОДИН проєкт, один репозиторій, один Railway-сервіс.** Головний сайт
(генератор прев'ю, замовлення) і застосунок складання — не два окремі
продукти, а дві сторінки того самого Express-сервера (`/` і `/assembly/`),
з однаковим `package.json`, `Dockerfile`, і спільним `server/config.js`
(де в одному місці лежать всі константи — кількість пінів, розмір рами
тощо, — тож обидві частини сайту завжди узгоджені між собою). Не потрібно
заводити другий репозиторій на GitHub чи другий сервіс на Railway.

## Як це працює (коротко)

1. Клієнт завантажує фото → кадрує в коло прямо в браузері (Cropper.js)
2. `POST /api/generate` → `convert.py` (адаптивно спрощує фон, конвертує в PGM)
   → C++ рушій (`bin/string-art`, компілюється з `cpp/`) плете 3800–4000 ліній
   → `pgm_to_image.py` конвертує результат у JPG
3. Файли зберігаються в `tmp/<sessionId>/` — ізольовано на кожен запит
4. При замовленні (`POST /api/order`) дані форми + обидва фото (оригінал і
   прев'ю) йдуть у Telegram-чат через Bot API; тимчасові файли видаляються
5. "Осиротілі" сесії (прев'ю згенероване, замовлення не оформлене)
   прибираються автоматично раз на годину

## Локальний запуск

Знадобляться: Node.js ≥20, Python 3 з `opencv-python-headless`, `g++`.

```bash
# 1. Скомпілювати C++ рушій
cd cpp
g++ -O2 -std=c++17 string-art.cpp Image.cpp StringArtImage.cpp StringArtist.cpp -o ../bin/string-art
cd ..

# 2. Python-залежності
pip install opencv-python-headless numpy --break-system-packages

# 3. Node-залежності
npm install

# 4. Змінні середовища
cp .env.example .env
# і заповнити TELEGRAM_BOT_TOKEN / TELEGRAM_CHAT_ID

# 5. Запуск
npm start
# або npm run dev для автоперезапуску (nodemon)
```

Сайт буде на `http://localhost:3000`.

## Застосунок складання (`/assembly/`)

Окрема сторінка того самого сервера — не окремий проєкт, не окремий деплой.
Клієнт отримує код замовлення (той самий `SA-YYYYMMDD-XXXX`, що приходить у
Telegram), сканує QR на картці інструкцій → відкриває `yourdomain.com/assembly/`
→ вводить код → бачить покрокову інструкцію плетіння з голосовим супроводом.

### Структура

```
public/assembly/
├── index.html          # екран входу + головний екран (SPA, без роутера)
├── css/assembly.css     # стилі, ті самі токени що на головному сайті
└── js/
    ├── sectors.js         # пін -> сектор (A1..D240, наскрізна нумерація), довжина нитки
    ├── wheel.js            # малює SVG-колесо 240 пінів, підсвічує поточний крок
    ├── voice.js             # Web Speech API: озвучка кроків укр/англ
    └── app.js                # вхід, навігація, автоплей, localStorage+синк

server/
├── services/orders.js    # постійне сховище data/orders/<код>.json
├── services/pinout.js     # текстовий файл розпіновки для Telegram (backup)
├── routes/assembly.js      # GET /api/assembly/:code, POST /api/assembly/:code/progress
└── middleware/rateLimit.js  # захист від підбору коду (окремо від sync-трафіку)
```

### Як генерується код доступу

Той самий код замовлення (`server/services/orders.js`), який іде в
Telegram-сповіщення при оформленні. Формат `SA-YYYYMMDD-XXXX` лишився без
змін; суфікс — 4 символи з алфавіту БЕЗ `0/O` та `1/I` (щоб не плутати при
диктовці по телефону чи передруку з SMS). Генерація перевіряє колізії проти
вже існуючих файлів у `data/orders/` і повторює спробу за потреби (до 20
разів, теоретично неможливо вичерпати).

### Звідки застосунок бере дані про картину

C++ рушій (`cpp/StringArtist.cpp`) тепер зберігає повну послідовність пінів
(`m_pinSequence`) і віддає її в `##RESULT##{"pins": [...]}`. При оформленні
замовлення (`server/routes/order.js`) ця послідовність переноситься з
тимчасової сесії `tmp/` у постійний запис `data/orders/<код>.json` — саме
звідти `/api/assembly/:code` її читає. Координати пінів НЕ передаються на
фронтенд — довжина нитки рахується на льоту через тригонометрію хорди
(`sectors.js`), знаючи лише кількість пінів і реальний діаметр рами
(`PIN_CIRCLE_DIAMETER_CM` у `server/config.js`).

**Нумерація пінів:** наскрізна 1-240 за годинниковою стрілкою (не окремий
лічильник 1-60 на кожен сектор!) — сектор A починається зліва на колесі
(не зверху) і охоплює номери 1-60, далі B=61-120, C=121-180, D=181-240.
Літера поруч із числом — це просто орієнтир, у якому секторі шукати пін
("C140" означає "піна №140 із загальних 240, він у секторі C"), а не
"140-й пін у секторі C" (такого не існує — у кожному секторі лише 60 пінів).
Уся логіка — в одній функції `pinToSector` (`public/assembly/js/sectors.js`),
яку через подвійну сумісність (`window.SectorUtils` у браузері,
`module.exports` у Node) використовують і фронтенд, і сервер (генерація
файлу розпіновки нижче) — гарантовано ОДНА формула, без ризику розійтися.

**Порядок секторів на колесі:** піни 0-59 фізично лежать у верхньо-правій
чверті кола, 60-119 — у верхньо-лівій, 120-179 — нижньо-ліва, 180-239 —
нижньо-права (математика кута в `wheel.js`). Свідомо позначені як
**B, A, D, C** (не по порядку індексів) — так за годинниковою стрілкою
літери йдуть логічно A→B→C→D по колу. Це ОДИН масив `SECTOR_LETTERS` в
`wheel.js` (для статичних підписів дуг) — там **інший** масив, ніж у
`sectors.js` (для нумерації 1-240), і це нормально: вони влаштовані
по-різному, але дають однакову літеру для кожної фізичної точки
(перевірено тестом на всіх 240 raw-індексах).

### Розпіновка в Telegram — підстраховка на випадок збою сайту

При кожному оформленні замовлення (`server/routes/order.js`) в Telegram
тепер летить не два файли, а три: два фото (як і раніше) + текстовий файл
`pinout-<код>.txt` з повною покроковою розпіновкою ("Крок 1847: B120 → D45"
для кожного з ~3800 кроків, той самий формат і нумерація, що на екрані
застосунку). Якщо сайт колись стане недоступний чи дані загубляться —
власник бізнесу може відкрити цей файл і продиктувати чи переслати клієнту
решту кроків вручну, без сайту.

Генерується в `server/services/pinout.js`, використовує ту саму функцію
`pinToLabel`, що й фронтенд (через require() — див. коментар у
`sectors.js` про подвійну сумісність). Реальний розмір файлу для повного
замовлення (~3800 кроків) — **~85-100 КБ**, надсилається окремим
`sendDocument`-викликом (Telegram media groups не змішують фото з
документами в одному альбомі).

### Надійність прогресу складання

Складання може тривати тижнями з перервами, тож просто `localStorage` — не
досить (очищення браузера, iOS Safari може прибирати дані сайтів, інший
пристрій/браузер). Стратегія — два рівні:

1. **localStorage** (`sa_progress_<код>`) — пишеться при КОЖНІЙ зміні кроку,
   основне джерело при поверненні на той самий пристрій/браузер.
2. **Сервер** (`data/orders/<код>.json`, поле `progress`) — підстраховка.
   Синхронізується не на кожен крок (це були б тисячі запитів за сесію), а
   раз на 15 кроків + примусово при паузі, переході на довільний крок,
   завершенні останнього кроку, і при згортанні/закритті вкладки (через
   `navigator.sendBeacon` — найнадійніший спосіб встигнути відправити
   запит, поки сторінка ще жива).

При вході: якщо `localStorage` для ЦЬОГО коду є — довіряємо йому (найсвіжіше,
і коректно відображає навіть свідомий відкат назад через кнопку Previous).
Якщо нема (інший пристрій чи очищено) — беремо крок із сервера.

**Rate limiting:** вхід за кодом (GET) і синхронізація прогресу (POST) мають
РІЗНІ ліміти. Вхід — суворий (20/15хв, захист від підбору коду). Синхронізація
прогресу — щедрий (300/15хв), бо це рутинний фоновий трафік під час активного
автоплею, а не спроба вгадати код.

### Скільки місця займають дані замовлень і автоочищення

Один запис замовлення (`data/orders/<код>.json`) — це переважно масив пінів
(~3800 чисел) + невеликі дані клієнта. Реально виміряний розмір одного
файлу: **≈13.6 КБ**. Тобто:

| Кількість замовлень | Місце на диску |
|---|---|
| 100 | ~1.3 МБ |
| 1 000 | ~13.3 МБ |
| 10 000 | ~132 МБ |

Тобто саме МІСЦЕ НА ДИСКУ — не проблема навіть за тисяч замовлень. Головна
причина автоочищення — не диск, а гігієна даних: не тримати вічно ПІБ,
телефон, адресу клієнта після того, як замовлення повністю виконане й
доставлене.

**Механізм** (`server/services/orders.js`, `cleanupCompletedOrders`):
- Коли клієнт доходить до останнього кроку складання — `progress.completedAt`
  проставляється автоматично (`updateProgress`).
  Якщо після цього людина повернулась назад (наприклад, ще раз глянути якийсь
  крок) — `completedAt` скидається в `null`, доки вона знову не дійде до кінця.
- Раз на добу (`server/index.js`) сервер сканує `data/orders/` і видаляє
  файли, де `completedAt` старший за `ORDER_RETENTION_DAYS_AFTER_COMPLETION`
  (за замовчуванням **10 днів**, змінюється в `server/config.js`).
- **Незавершені замовлення НІКОЛИ не видаляються за віком** — перевірено
  окремим тестом: замовлення з `createdAt` рік тому, але не завершене,
  лишається недоторканим. Людина може призупинити складання на будь-який
  термін без ризику втратити прогрес.



Web Speech API (`window.speechSynthesis`), українською й англійською.
Числа й сектори промовляються словами ("Від сектора Бі, дванадцять, до
сектора Ді, сорок п'ять"), а не побуквено. Якщо на пристрої немає системного
українського голосу (поширена ситуація поза macOS/iOS з увімкненою укр.
мовою) — застосунок чесно перемикається на англійську (і голос, і текст
одночасно, щоб не читати українську фразу англійською вимовою) і показує
коротке пояснення під перемикачем мови.

**Важливо розуміти обмеження тестування:** я перевірив усю логіку
(генерація тексту, перемикання мов, mute/unmute, збереження вподобань,
спрацювання фолбеку) через Playwright з перехопленим `speechSynthesis.speak`
— тобто підтвердив, що застосунок ПРАВИЛЬНО ФОРМУЄ запити на озвучку. Але
headless Chromium у середовищі розробки не має жодного встановленого
системного голосу (звичайна властивість серверних/CI-браузерів), тож я не
чув живого звуку і не можу підтвердити якість вимови реальним українським
чи англійським голосом — це варто перевірити наживо на телефоні клієнта
після деплою.

### ⚠️ Volume на Railway — критично

`data/orders/` **обов'язково** потребує Railway Volume, підключеного саме на
цей шлях (`DATA_DIR` у `server/config.js`, за замовчуванням `./data`). Без
Volume кожен redeploy стирає всі замовлення й прогрес складання клієнтів —
на відміну від `tmp/` (яка мала б чиститись), ці дані повинні жити тижнями.



1. Запушити репозиторій у GitHub
2. Railway → New Project → Deploy from GitHub repo (Railway сам побачить
   `Dockerfile` і збере образ)
3. Railway → Variables → додати `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`
   (значення з `.env`, сам `.env` у git не потрапляє — див. `.gitignore`)
4. Railway автоматично прокидає `PORT` — код це вже враховує
   (`server/config.js` читає `process.env.PORT`)
5. Готово — Railway видасть публічний URL

### Нотатка про продуктивність

Одна генерація зараз займає ~10-15 секунд (перевірено на тестовому фото).
Railway за замовчуванням має таймаут на HTTP-запит — якщо колись буде
помітно довше (дуже завантажений сервер, важкі фото), варто або підняти
таймаут у Railway, або винести генерацію в чергу (наприклад через
Railway cron/worker) замість синхронної відповіді на запит. Для старту
поточного підходу (синхронно, чекаємо відповіді) достатньо.

## Обмеження й чесні застереження

- `Dockerfile` написаний і ретельно перевірений вручну (шляхи, версії
  пакетів, послідовність шарів), але **не зібраний насправді** — у
  середовищі розробки немає Docker-демона. Перший `docker build` варто
  прогнати самостійно перед деплоєм на Railway.
- Google Fonts / Cropper.js підключені через CDN (`cdnjs`, `fonts.googleapis.com`)
  — стандартний підхід, працює в будь-якому браузері з інтернетом, окремої
  збірки не потребує.
